# Фаза 1: Подготовка (шаги 0–3)

Эта фаза готовит входные данные для перевода: исходная книга
конвертируется в чанки, собирается структурная информация (эпиграфы,
сноски, narrator hints), и создаётся глоссарий + голос книги.

**После завершения фазы 1 — обязательная точка сжатия контекста**
(см. `references/compaction-points.md`).

---

## Шаг 0. Опционально: Pretest / quick-sample

**Когда использовать:** при прямом запросе пользователя, или если
качество перевода вызывает сомнения и нужен быстрый sanity-check
перед полным прогоном.

1. Создай минимальный глоссарий на главе 1–2 и голос (`templates/`).
2. Запусти `convert.py`. Узнай общее число чанков.
3. Вручную переведи **первые 2–3 чанка** через те же субагент-инструкции,
   что используются в шаге 5.
4. Оцени результат:
   - Терминология устраивает? → глоссарий OK.
   - Голос устраивает? → голос OK.
   - Типичные системные ошибки видны сразу? → настрой промпты при необходимости.
5. Если что-то не устраивает — правь `templates/*.md`, глоссарий, промпты
   и запускай pretest заново. **Не запускай полный прогон, пока pretest
   не одобрен.**

## Шаг 1. Подготовка

Перед запуском убедиться, что есть:

| Что | Где взять |
|-----|-----------|
| Английский оригинал | .epub / .fb2 / .pdf / .docx |
| Словарь терминов | создать по `templates/словарь_терминов.md` |
| Голос книги | создать по `templates/голос_книги.md` |

Словарь и голос можно создать сразу, а можно отложить до шага 3
(глоссарий соберётся из сэмплов, а голос — после прочтения начала книги).

### 1.1. Для книги из серии — ОБЯЗАТЕЛЬНО изучить официальные переводы предыдущих книг

Если переводимая книга — часть серии и **существуют официальные
(или любые качественные) переводы предыдущих книг серии**, оркестратор
**обязан** до начала перевода:

1. **Найти FB2/EPUB предыдущих книг** в любой удобной директории
   (спросить пользователя, где они лежат, если не очевидно).
2. **Извлечь из них стиль и терминологию:**
   - Запусти `python3 {baseDir}/scripts/phase1_prepare/explore_epub.py`
     на каждом FB2/EPUB предыдущей книги — это даст заголовки, автора,
     структуру.
   - Если FB2 — конвертируй в Markdown через
     `pandoc <file>.fb2 -f fb2 -t markdown --wrap=none -o <file>.md`
     (или через `convert.py` с флагом `--temp-root` в отдельную папку,
     чтобы не смешать с переводом текущей книги).
   - **Прочитай первые 2–3 главы** предыдущей книги — для понимания
     тона, регистра, ритма, обращения к читателю (например, в серии
     «Алькатрас» Брэндона Сандерсона — это ироничный 1-й лиц, прямое
     обращение к читателю, активное разрушение 4-й стены).
   - **Выпиши в `словарь_терминов.md`** все имена собственные, термины
     мира, магические системы, организации, географию — с **теми
     русскими соответствиями, что уже закреплены** в предыдущих книгах.
     Это не «опционально» — это страховка от расхождения терминологии
     между книгами серии.
3. **Заполни `голос_книги.md`** на основе предыдущих книг: POV-голоса,
   регистр, ирония, обращения к читателю, особые стилистические приёмы.
4. **Если предыдущих переводов нет** — явно отметь в `голос_книги.md`,
   что перевод «с нуля», и иди по обычному пути (шаг 3 соберёт
   глоссарий из чанков, голос — по первым главам).

> **Антипаттерн из реального прогона:** при переводе 4-й книги серии
> «Алькатраз» оркестратор проигнорировал FB2 первых трёх книг,
> переведённых официально. Результат — расхождения в именах, стиле
> обращения к читателю, ритме. Это потребовало ручной правки после
> перевода. **Не повторяй эту ошибку.**

## Шаг 1.5. (Для EPUB) Исследование структуры — explore_epub.py

**Если входной файл — EPUB**, запусти скрипт исследования **перед**
`convert.py`. Это даёт быстрый обзор содержимого без ad-hoc
`python3 -c "..."` команд, которые часто падают на Windows.

```bash
python3 {baseDir}/scripts/phase1_prepare/explore_epub.py "<путь_к_файлу.epub>"
```

**Что выведет скрипт** (UTF-8, работает на Windows):
- Метаданные из OPF (title, author, language, identifier)
- Spine — порядок чтения файлов
- Главы из NCX (названия + пути к файлам)
- Список всех HTML/XHTML файлов с размерами
- Заголовки H1/H2, найденные в первых 20 файлах (для детекции глав)
- Summary: оценка числа чанков, размер контента

**Зачем это нужно:**
1. Узнать структуру книги до конвертации (есть ли главы? какие
   заголовки? есть ли NCX с нормальными названиями?).
2. Понять, сколько примерно чанков получится — оценить стоимость прогона.
3. Не тратить контекст главного агента на ad-hoc python-сниппеты.

**Для FB2/PDF/DOCX** — этот шаг пропускается (скрипт только для EPUB).
Для этих форматов структура видна уже после `convert.py` в
`chunk_sections.json`.

## Шаг 2. Конвертация и чанкование

Есть **два конвертера** — выбери подходящий по симптомам:

| Симптом | Конвертер |
|---------|-----------|
| Стандартный EPUB/FB2/PDF, чистая структура | `convert.py` (Calibre→pandoc) |
| EPUB с calibre-спанами, split headings, raw HTML images | `convert_per_file.py` (per-file pandoc + cleanup) |

### 2a. Стандартный путь: `convert.py`

```bash
python3 {baseDir}/scripts/phase1_prepare/convert.py "<путь_к_файлу>" \
    [--force] [--no-chapter-split] [--chapter-only]
```

Скрипт делает:
1. Конвертирует EPUB/FB2/PDF → Markdown через Calibre + Pandoc
   (промежуточные htmlz/extracted файлы кладёт в `process/`)
2. Разбивает Markdown **по границам H1/H2** (chapter-aware) на секции.
   По умолчанию (`chapter_only = true`) одна секция = один чанк (главы
   не режутся по размеру). Если `chapter_only = false` — каждая секция
   дробится на чанки по **~30000 символов** (из `config.toml`) с резкой
   по границе абзаца (предложения — только для абзацев > 40000)
3. Создаёт `manifest.json` (version 2) с SHA-256 каждого чанка + название
   раздела (`section_title`, `section_level`)
4. Создаёт `chunk_sections.json` — sidecar для отладки и QA
5. Создаёт `source_fingerprint.json` — SHA-256 входного файла
6. Записывает метаданные в `config.txt`
7. **Автоматически вызывает `detect_epigraphs.py`, `narrator_marker.py`,
   `extract_footnotes.py`** (шаг 2.5).

**Параметры**:
- `--no-chapter-split` — если Markdown с плохой структурой заголовков
- `--chapter-only` — один чанк = одна глава (без разбиения по размеру).
  Это **режим по умолчанию** (`config.toml [chunking] chapter_only = true`).
  Рекомендуется для художественной прозы — сохраняет целостность главы
  для контекста субагента. Если главы очень длинные (>50000 символов) —
  переключи `chapter_only = false` в config.toml.
- `--force` — пропустить safety gate
- `--temp-root <dir>` — альтернативный родитель для `_temp/`

### 2b. Альтернативный путь: `convert_per_file.py` (для проблемных EPUB)

```bash
python3 {baseDir}/scripts/phase1_prepare/convert_per_file.py "<путь_к_epub>" \
    [--force] [--temp-root <dir>] [--exclude-file <json>] [--title-map <json>]
```

**Когда использовать:** если `convert.py` выдаёт:
- Много крошечных чанков (< 200 символов) — одни заголовки/номера глав
- `chunk_sections.json` содержит calibre-ссылки вместо названий глав
- В `input.md` видны `tfhabitatexpanded_bold_b_`, `calibre_link`,
  `pagebreak`, `{.minio}`, сырой HTML `<figure><img>` вместо Markdown
- Заголовки глав разбиты на 2 строки (слово "Chapter" отдельно от номера)

**Что делает `convert_per_file.py`:**
1. Распаковывает EPUB как zip, читает OPF spine
2. Для каждого XHTML из spine гонит `pandoc html→markdown` **отдельно**
   (не через объединённый HTMLZ) — сохраняет чистую структуру глав
3. Чистит каждый Markdown (`clean_md()`):
   - **Сначала заголовки** (пока жив маркер `tfhabitatexpanded_bold_b_`):
     первая строка → чистый `# Chapter N` по имени файла, вторая (номер) удаляется
   - Удаляет pagebreak-спаны `{#pg_...}`, буквицы `[X]{.minio}`,
     calibre-ссылки `[[text](#calibre_link-N)]`, pandoc-атрибуты `{...}`,
     div-фенсы `:::`
   - `<figure><img>` и `<img>` → `![image](images/<name>)` (с нормализацией пути)
   - Убирает пустую строку сразу после `#` (чтобы заголовок не отваливался
     в отдельный 9-символьный чанк)
4. Копирует все картинки EPUB в `process/images/`
5. Отсекает издательский мусор (cover, title, mini_toc, copyrightnotice,
   contents, adcard, newsletter, copyright, torad)
6. Переиспользует `split_into_chunks()` из `convert.py` для чанкования
7. Запускает post-steps: detect_epigraphs, narrator_marker, extract_footnotes

**Параметры:**
- `--exclude-file <json>` — JSON-массив дополнительных имён файлов для исключения
  (по умолчанию уже исключены: cover, title, mini_toc, copyrightnotice,
  contents, adcard, newsletter, copyright, torad, toc, tableofcontents,
  imprint, halftitle)
- `--title-map <json>` — JSON-объект `{basename: "Chapter Title"}` для
  нестандартных имён файлов. По умолчанию `chapter1` → "Chapter 1",
  `prologue` → "Prologue", `epilogue` → "Epilogue", и т.д.
- `--force` — пропустить safety gate
- `--temp-root <dir>` — альтернативный родитель для `_temp/`

> **⚠️ Важно:** `convert_per_file.py` **не поддерживает `--chapter-only`**
> (всегда режет по размеру ~30000 символов). Если в `config.toml` стоит
> `chapter_only = true` — он будет молча проигнорирован. Если нужна
> chapter-only семантика на проблемном EPUB — сначала прогони
> `convert_per_file.py`, потом склей чанки вручную (или используй
> `convert.py --chapter-only` на уже очищенном `input.md`).

**Результат (одинаковый для обоих конвертеров):**
`<имя>_temp/chunk0001.md … chunkNNNN.md`, `manifest.json`,
`chunk_sections.json`, `source_fingerprint.json`, `config.txt`,
`structural_units.json`, `narrator_hints.json`, `footnotes_extracted.json`
(если есть EPUB-сноски), `images/` (если есть картинки).

**Safety gates (для обоих конвертеров):**
- Если `source_fingerprint.json` существует и SHA-256 источника отличается
  от текущего файла, скрипт отказывается перезаписывать манифест без `--force`.
- Если в `<книга>_temp/` уже есть `output_chunk*.md`, скрипт отказывается
  перезаписывать манифест без `--force`.

**Почему chapter-aware**: глоссарий не ломается на границе повествовательных
единиц. Очень короткие главы (< 5000 символов) могут склеиться; очень
длинные (> 40000) — режутся по границе абзаца.

**Предупреждение**: если `convert.py` сообщает «N chunks shorter than 200»,
значит, разбиение прошло по границе короткого хвоста. Это не ошибка,
но такие чанки стоит просмотреть — обычно это короткие заголовки, которые
стоит склеить с соседом. Если таких чанков много — переключайся на
`convert_per_file.py`.

## Шаг 2.5. Structural extract (эпиграфы, сноски, narrator hints)

`convert.py` автоматически вызывает три вспомогательных скрипта после
чанкования. Все — **детерминированные**, никакого LLM:

```bash
# Запускается автоматически из convert.py; вручную можно:
python3 {baseDir}/scripts/phase1_prepare/detect_epigraphs.py "<temp_dir>"
python3 {baseDir}/scripts/phase1_prepare/narrator_marker.py "<temp_dir>"
python3 {baseDir}/scripts/phase1_prepare/extract_footnotes.py "<temp_dir>" [--epub <path>]
```

### 2.5a. `detect_epigraphs.py`

Находит **структурно** (не понимая смысла):
- **Эпиграфы** — короткие блоки текста перед заголовками глав (часто
  с атрибуцией типа `— Author`).
- **Сноски** — `[^N]` маркеры в тексте + `[^N]: ...` определения.
- **Inline-цитаты** — блочные цитаты (`> ...`), которые могут оказаться
  важным культурным материалом.

Выход: `<temp_dir>/process/structural_units.json`.

**Этот скрипт НЕ переводит и НЕ решает**, что делать с эпиграфом —
только находит и записывает. Все решения по переводу принимает LLM-агент
на шаге 5 (внутри `output_chunkNNNN.meta.json`) и на шаге 8 (внутри polish).

### 2.5b. `narrator_marker.py`

Группирует чанки по **структурным** heading-паттернам:
- `Interlude 1`, `Interlude 2` → разные arcs
- `Chapter 5` → один arc (но несколько глав подряд = один arc)
- `Prologue`, `Epilogue`, `Part II` → свои arcs

Выход: `<temp_dir>/process/narrator_hints.json`.

**Этот скрипт НЕ определяет, кто рассказчик.** Группировка по heading'ам —
это не POV. Конкретный narrator решает **субагент на шаге 5** через
`prompts/phase2_translate/определение_рассказчика.md` и поле
`narrator_identification` в meta.json.

### 2.5c. `extract_footnotes.py` (КРИТИЧНО для EPUB с отдельным файлом сносок)

**Проблема, которую решает:** некоторые EPUB (особенно Brandon Sanderson
от Tor) кладут **тела сносок** в отдельный XHTML-файл (например,
`OEBPS/Text/part0039.xhtml`) в виде
`<li epub:type="footnote" id="...">...</li>`. В основном тексте
содержатся только якоря вида
`[[*](part0039.xhtml#ID){#localid .noteref}]{.epub-sup-fn}`.

Когда `convert.py` запускает pandoc на largest HTML-файле, он **не видит**
файл со сносками — якоря превращаются в сырую pandoc-разметку, а тела
сносок вообще не попадают в `chunkNNNN.md`. Субагенты перевода копируют
сырую разметку в русский вывод, и FB2-сборщик не может их связать —
мёртвые ссылки.

**Что делает скрипт:**
1. Ищет `_epub_extracted/` или `htmlz_extracted/` в `process/`. Если
   не находит — пере-извлекает EPUB (нужен `--epub <path>`).
2. Сканит все XHTML-файлы на `<li epub:type="footnote" id="...">...</li>`
   — извлекает и чистит тела (HTML → Markdown: `<i>`→`*...*`,
   `<b>`→`**...**`, удаляет `<a class="reversefootnote">`, unescape).
3. Сканит все `chunkNNNN.md` на EPUB-якоря (несколько форматов pandoc —
   см. `ANCHOR_PATTERNS` в скрипте).
4. Для каждого якоря назначает **глобально уникальный номер** (1..N по
   всей книге, не по главам) и заменяет якорь на `[^N]`.
5. Дописывает определения `[^N]: <перевод тела>` в конец того чанка,
   где якорь **впервые** встречается. Если тот же `footnote_id`
   referenced из другого чанка — номер переиспользуется, определение
   не дублируется.
6. Пишет `process/footnotes_extracted.json` с аудитом маппинга.

**Почему глобальная нумерация:** `fb2_builder.py` собирает все `[^N]:`
определения в один `<body name="notes">`. При поконовой нумерации
`[^1]` продублировался бы и дал коллизии `id="note_1"` в FB2.

**Если скрипт не нашёл сносок** — он завершается с `exit 0` (не ошибка).
Книги без EPUB-style сносок просто пропускают этот шаг.

**Если в EPUB есть сноски, но `_epub_extracted/` не найден:**
```bash
python3 {baseDir}/scripts/phase1_prepare/extract_footnotes.py "<temp_dir>" --epub "<path_to_source.epub>"
```

**Аудит после извлечения:**
```bash
# Проверь, что все якоря заменены (не должно быть "epub-sup-fn" или "noteref" в чанках):
grep -l "epub-sup-fn\|noteref" <temp_dir>/process/chunk*.md
# Должно вернуть пусто.

# Проверь, что определения есть:
grep -c "^\[\^[0-9]\+\]:" <temp_dir>/process/chunk*.md | head
```

### Зачем нужен этот шаг

- **Шаг 5 (translate)**: субагент получает `structural_units.json`
  (если в чанке есть эпиграф/сноска — он их обрабатывает по
  `prompts/phase2_translate/эпиграф_обработка.md`) и `narrator_hints.json`
  (он знает, к какому arc принадлежит чанк и не «усредняет» голос).
- **Шаг 7.5 (QA)**: QA-агент видит, есть ли в чанке эпиграф, и проверяет
  его отдельно.
- **Шаг 7.6 (pronoun check)**: агенту доступны narrator hints.
- **Шаг 8.5 (post-mortem)**: эпиграфы агрегируются как отдельная сущность
  с собственными рисками.
- **Шаг 9 (build)**: `fb2_builder.py` собирает все `[^N]:` определения
  (включая те, что добавил `extract_footnotes.py`) в `<body name="notes">`,
  и якоря `[^N]` → `<a xl:href="#note_N">`. Без `extract_footnotes.py`
  сноски были бы мёртвыми ссылками.

## Шаг 3. Сбор глоссария

Если `glossary.json` уже существует — **не перезаписывать** (пользователь
мог править вручную или переносить из серии).

### 3.0. Если глоссарий от ПРЕДЫДУЩЕГО прогона той же книги — сбрось run-state

Если `glossary.json` содержит `applied_meta_hashes` или per-term
`evidence_refs`/`notes` — это метаданные от предыдущего прогона. Если
запустить новый прогон с ними, `merge_meta.py` может счесть старые
чанки «уже применёнными» (по `applied_meta_hashes`) и пропустить их
молча — глоссарий не обновится.

**Перед свежим прогоном той же книги:**
```bash
python3 {baseDir}/scripts/phase1_prepare/glossary.py reset-run-state "<temp_dir>"
```

Сделает:
- Удалит `applied_meta_hashes` (top-level)
- Удалит per-term `evidence_refs` и `notes`
- Сохранит канонические поля: `source`, `target`, `aliases`, `category`,
  `gender`, `confidence`, `frequency`

**Если глоссарий — series-wide (перенесён из других книг серии):**
```bash
python3 {baseDir}/scripts/phase1_prepare/glossary.py reset-run-state "<temp_dir>" --prune-zero-freq
```
Дополнительно удалит термины с `frequency == 0` (не встречаются в этой
книге). После этого **обязательно пересчитай частоты:**
```bash
python3 {baseDir}/scripts/phase1_prepare/glossary.py count-frequencies "<temp_dir>"
```

### 3.1. Сбор глоссария с нуля

Если `glossary.json` ещё нет:

1. Прочитать первый чанк, последний, и 3 равномерно распределённых средних.
2. Из каждого извлечь имена собственные, термины мира, повторяющиеся понятия.
3. Определить для каждого целевой перевод.
4. Записать `glossary.json` (схема — см. `references/meta-json-schema.md`).
5. Подсчитать частоты по всем чанкам:

```bash
python3 {baseDir}/scripts/phase1_prepare/glossary.py count-frequencies "<temp_dir>"
```

После этого можно отредактировать `glossary.json` вручную, если нужно
поправить варианты перевода, добавить алиасы, повысить confidence.

### 3.2. Checkpoint: проверка глоссария пользователем

**После шага 3 — обязательная пауза.** Сообщи пользователю:

> Глоссарий собран: N терминов, M алиасов. Файл: `<temp_dir>/glossary.json`.
> Перед запуском перевода проверь:
> 1. Имена персонажей — правильные ли русские соответствия?
> 2. Термины мира (магия, география, организации) — соответствуют ли
>    предыдущим переводам серии (если есть)?
> 3. Категории (person/place/org/term) — не перепутаны ли?
> 4. Gender — заполнен ли для известных персонажей?
>
> Отредактируй `glossary.json` вручную, если нужно. После правки
> пересчитай частоты:
> `python3 {baseDir}/scripts/phase1_prepare/glossary.py count-frequencies "<temp_dir>"`
>
> Ответь «продолжить», когда глоссарий готов.

**Не запускай шаг 4 (перевод) без явного подтверждения пользователя.**
Ошибки в глоссарии на этом этапе — самые дорогие: они размножатся на все
чанки и потребуют полного повторного перевода.

Если пользователь предоставил `голос_книги.md` — тоже предложи проверить
его на этом же checkpoint.

### 3.3. После подтверждения глоссария — ТОЧКА СЖАТИЯ КОНТЕКСТА

Когда пользователь подтвердил глоссарий (и, опционально, голос книги):

1. **Запиши состояние** в `progress.json`:
   ```bash
   python3 {baseDir}/scripts/shared/save_state.py "<temp_dir>" 3 \
       --note "Глоссарий собран и подтверждён пользователем" \
       --set glossary_path="<temp_dir>/glossary.json" \
       --set voice_path="<temp_dir>/голос_книги.md" \
       --set total_chunks=<N>
   ```
2. **Предложи пользователю сжать контекст:**
   > Глоссарий зафиксирован (N терминов, M алиасов). Дальше — планирование
   > и перевод, которые не требуют содержимого чанков в моём контексте.
   > **Рекомендую сжать контекст сейчас** перед началом фазы 2.
3. Если пользователь согласился — выполни compact. Если нет — продолжай
   без сжатия. **Никогда не делай compact автоматически без предложения.**
4. После compact (или без него) — переходи к фазе 2: прочитай
   `references/phase-2-translate.md` и начни с шага 4.

Подробнее про точки сжатия: `references/compaction-points.md`.

## Что важно помнить на этой фазе

- **Не подгружай чанки в контекст оркестратора.** Если нужно посмотреть
  содержимое — используй `head -50 chunkNNNN.md` через bash, не
  read_file в основной поток.
- **После `convert.py` проверь `manifest.json`** — количество чанков,
  размеры. Аномально маленькие (<200) чанки — обычно bad split.
- **Все детерминированные шаги уже сделаны скриптами** к концу фазы 1.
  Глоссарий и голос — это LLM-работа, но её выполняет оркестратор (как
  исключение), а не субагент.
